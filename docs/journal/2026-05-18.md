# 📚 Journal de Bord — 2026-05-18 : CI / Webhook de notification d'échec

## 🎯 Objectifs & Périmètre
- Amélioration de l'observabilité et de la réactivité de l'équipe face aux éventuelles pannes d'intégration ou de déploiement continu.
- Mise en place d'une alerte automatisée notifiant immédiatement Kuroko (le Chef d'Orchestre) dès qu'un échec de build ou de transfert SSH survient sur la branche `main`.
- Sécurisation du protocole d'émission via un webhook HTTP POST chiffré.

## 🛠️ Modifications & Fichiers impactés
- `.github/workflows/deploy.yml` :
  - Ajout de l'étape conditionnelle `🚨 Notify Kuroko of failure` s'exécutant uniquement en cas d'incident (`if: failure()`).
  - Consommation du secret d'organisation `FAILURE_WEBHOOK_URL`.
  - Formatage d'une charge utile JSON enrichie : nom du dépôt, identifiant du run GitHub Actions et message d'erreur contextuel.
- Commits associés :
  - `1b0367e5` : *ci: add failure webhook notification to Kuroko*

## 🐛 Problèmes, Bugs & Régressions rencontrés
- **Échecs silencieux en production** : En l'absence de notification push, un build cassé ou une coupure réseau SSH ne pouvait être remarqué qu'en consultant l'onglet Actions de GitHub manuellement, retardant la correction d'éventuels bugs en ligne.

## 💡 Solutions retenues & Arbitrages techniques
- Utilisation de `curl` dans le runner Linux pour expédier le payload JSON avec un en-tête `Content-Type: application/json`.
- Mécanisme de fallback non bloquant : si la variable d'environnement `FAILURE_WEBHOOK_URL` n'est pas renseignée, le script émet un warning dans les logs du runner sans provoquer d'erreur parasite supplémentaire.

## ⚠️ Points de vigilance pour le futur
- S'assurer que le secret GitHub `FAILURE_WEBHOOK_URL` est bien maintenu actif et renouvelé lors des rotations de jetons webhook.
